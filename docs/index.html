01

The problem

Every client proposal—Audit, Advisory, Tax—is a 50–60 slide branded PowerPoint draft. Today we assemble those drafts with Templafy, a third-party tool, from a bank of branded templates and slides.

Templafy works, but its license is expensive. And when we looked closely, we realised that most of what it does is pure automation: pick the right slides for the request, drop in the client name, date and city, and apply the brand. If that part is mechanical, we can do it ourselves and stop paying for it.

The question this POC answers: how much of Templafy can we replace deterministically—and how faithfully?

02

What Templafy does today

A user answers a short form—service line, client, due date, industry sector, office city, and a set of yes/no options. Templafy then assembles the deck:

1 · Answer the form
service line, client, date, sector, city, optional sections
→
2 · Assemble
keep / drop slides from a master, fill text & images, apply branding
→
3 · Branded draft
a ready-to-edit proposal deck

Two kinds of content go into that deck: deterministic pieces (which slides, the client name, the city—decided purely by the answers) and a few data-driven pieces (fee tables, partner names, RFP responses) that Templafy pulls from connected data sources. That split turns out to be the whole story.

03

What we built

A small app with a simple idea: learn the rules once from Templafy’s own output, then rebuild any deck ourselves. It runs in four stages.

The core idea, in one line

It is not AI and not guesswork—it is deterministic assembly. Templafy’s output is consistent, so we can measure exactly what changes for every option and replay it.

  • □Baseline. One standard deck is the starting point for every rebuild.
  • +Blocks. Each answer (a toggle, a sector, a city) adds, removes or swaps a precise set of slides—learned by comparing decks.
  • ≈Tokens. The client name and date are filled in as text, everywhere they appear.
  • ✓Proof. Every rebuild is compared to Templafy’s real deck, slide by slide, to confirm it’s identical.

05

What’s left, and the path to 100%

The only thing the engine can’t reproduce is the ~3–5 data-driven slides per deck: the fee assumptions, the named lead partner, the RFP cross-reference table. Templafy fills these from connected data sources (profile, finance, RFP systems)—so the numbers and names change per engagement, and we simply don’t hold that data yet.

manual today

Those data slides are filled by the engagement team anyway—Templafy often leaves the partner name as a <FirstName> placeholder too. So a proposal can ship now with those few slides completed by hand.

path to 100%

Connect the same data sources Templafy uses (profile → partner, finance → fees, RFP system). Those ~5 slides then auto-fill, closing the last ~8% with no change to the rest of the engine.

Keeping the rules correct over time

Branded content changes. The engine is built so a non-technical user can keep it current—no code:

  • ↻Template updated? Re-generate the reference decks and click Build library once—the rules relearn themselves automatically.
  • 🔧A small wording miss? The Fixups screen lets a user add a plain find-and-replace correction—and the app suggests the fix straight from the comparison, so they just confirm it.
  • ✅Confidence built in. A structural check and a slide-by-slide Diff run automatically, so a broken or drifted deck is caught before anyone opens it.

Manual effort remaining, per deck: only the few data-driven slides—and only until the data sources are connected. Everything else is one click.

06

Extending to other templates

This POC covers one template (the public-audit proposal). The engine itself is template-agnostic—it learns from whatever decks you give it. Onboarding another template (a different service line, a new region, a refreshed brand) is a data task, not an engineering task:

  1. Drop the new template’s master deck into its own asset folder.
  2. Generate reference decks for that template’s input values (one per option).
  3. Click Build library — the engine harvests the new rules on its own.
  4. Reconstruct & Diff to validate — same screens, same one-click checks.

Each template keeps its own library, so templates never interfere with each other, and the same app scales across the whole proposal catalogue—replacing the Templafy license everywhere it’s used.
